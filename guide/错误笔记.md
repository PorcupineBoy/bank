> 格式：错误场景 → 错误原因 → 解决方案

## 错误 1：Redis 存储 BigDecimal 序列化异常

| 字段 | 内容 |
|------|------|
| **错误时间** | 2026-04-23 |
| **错误场景** | 转账限额校验时，从 Redis 读取当日累计转账金额并强转为 `BigDecimal`，抛出 `ClassCastException` |
| **错误原因** | `redisTemplate.opsForValue().get(dailyKey)` 直接强转 `(BigDecimal)`，但 Redis 默认 JDK 序列化存储 `BigDecimal` 对象后读取出来实际类型为 `String`，无法直接强转 |
| **错误类型** | 数据类型处理错误（数据序列化/反序列化） |
| **错误文件** | `bank-backend/src/main/java/com/bank/service/impl/TransactionServiceImpl.java` |
| **错误代码** | `BigDecimal dailyUsed = (BigDecimal) redisTemplate.opsForValue().get(dailyKey);` |
| **解决方案** | 存入 Redis 前调用 `.toPlainString()` 转为字符串；读取时以 `(String)` 获取，再通过 `new BigDecimal(dailyUsedStr)` 构造 |
| **关联文件** | `TransactionServiceImpl.java` 第 174-176 行、第 216 行 |
| **经验教训** | RedisTemplate<String, Object> 使用 JDK 序列化时，存取数字类型必须统一用 String 中转，不可直接强转数值类型。涉及 Redis 存取的数值操作（限额、失败次数等）都需要检查 |

## 错误 2：转账防重锁竞态条件

| 字段 | 内容 |
|------|------|
| **错误时间** | 2026-04-27 |
| **错误场景** | 向同一收款人短时间内连续发起两次转账请求，两次均执行成功，防重锁未生效 |
| **错误原因** | 使用 `hasKey()` 检查锁是否存在 + `set()` 设置锁，两步操作非原子性。并发场景下两个请求同时通过 `hasKey` 检查，都会绕过锁限制 |
| **错误类型** | 并发/竞态条件错误 |
| **错误文件** | `bank-backend/src/main/java/com/bank/service/impl/TransactionServiceImpl.java` |
| **错误代码** | `if (redisTemplate.hasKey(lockKey)) { throw ... } redisTemplate.opsForValue().set(lockKey, "1", ...);` |
| **解决方案** | 改用 `redisTemplate.opsForValue().setIfAbsent()` 原子操作，一条命令完成"检查并设置" |
| **关联提交** | commit `41b075c` |
| **经验教训** | Redis 分布式锁必须使用原子操作（SETNX / setIfAbsent），不得先检查再设置。涉及并发控制的 Redis 操作都要检查原子性 |

## 错误 3：支付（缴费）功能缺少防重锁机制

| 字段 | 内容 |
|------|------|
| **错误时间** | 2026-04-27 |
| **错误场景** | 生活缴费（话费、水电费）功能在短时间内重复提交，同一账单被扣款多次 |
| **错误原因** | 实现支付功能（`payBill`）时，完全没有添加任何防重锁机制，而转账功能（`transfer`）是有防重锁的，说明代码复用意识不足 |
| **错误类型** | 功能缺失/遗漏错误 |
| **错误文件** | `bank-backend/src/main/java/com/bank/service/impl/TransactionServiceImpl.java` |
| **解决方案** | 为支付功能增加与转账相同的原子性防重锁（SETNX），key 区分前缀 `payment:` |
| **关联提交** | commit `41b075c` |
| **经验教训** | 同类功能（转账、缴费、支付等涉及资金操作）必须统一考虑防重/防抖机制，不能只在一处实现 |

## 错误 4：消费分类查询使用金额符号判断类型——逻辑错误

| 字段 | 内容 |
|------|------|
| **错误时间** | 2026-04-27 |
| **错误场景** | 实际有转账支出，但消费分析页查不到任何消费分类记录；同时出现重复的消费分类记录 |
| **错误原因** | `TransactionCategorizationServiceImpl` 中查询支出交易使用了 `.lt(amount, 0)`（金额小于零判断），但转账金额在 `transfer()` 中已经用 `.negate()` 转为负数存储到数据库，所以 `amount < 0` 的条件对所有转账都成立，导致：①某些查询路径查不到支出，②另一些路径产生重复记录 |
| **错误类型** | 业务逻辑判断错误 |
| **错误文件** | `bank-backend/src/main/java/com/bank/service/impl/TransactionCategorizationServiceImpl.java` |
| **错误代码** | `.lt(Transaction::getAmount, BigDecimal.ZERO)` |
| **解决方案** | 改为用交易类型字段判断：`.ne(Transaction::getTransType, Constants.TRANS_TYPE_INCOME)`（非收入即支出），不依赖金额正负 |
| **关联提交** | commit `41b075c` |
| **经验教训** | 数据库已有明确的类型字段时，查询条件应优先使用类型字段而非数字正负判断。金额正负可能因业务处理（.negate()）变得不可靠 |

## 错误 5：银行卡号 AES 解密失败

| 字段 | 内容 |
|------|------|
| **错误时间** | 2026-05-05 19:46 |
| **错误场景** | 查询银行卡列表时，银行卡号解密失败，日志重复出现 `Failed to decrypt card number for cardId=10` |
| **错误原因** | cardId=10 的数据库记录中 `card_no_encrypted` 字段存储的密文可能因密钥变更、数据损坏或不完整的写入（AES-CBC 模式要求固定块大小）导致解密异常 |
| **错误类型** | 数据加密/解密错误 |
| **错误文件** | `bank-backend/src/main/java/com/bank/service/impl/BankCardServiceImpl.java` |
| **错误代码** | `vo.setCardNo(AESUtil.decrypt(card.getCardNoEncrypted()));`（无异常处理） |
| **解决方案** | 添加 try-catch 捕获解密异常，失败时回退显示脱敏卡号（`card.getCardNoMasked()`），并在日志记录警告 |
| **经验教训** | 加密数据操作必须添加异常保护，避免单条数据异常导致整个列表查询失败。生产环境应考虑密钥管理（KMS）和数据完整性校验 |

## 错误 6：MySQL 长连接断开导致 HikariCP 连接池耗尽

| 字段 | 内容 |
|------|------|
| **错误时间** | 2026-05-05 20:11 |
| **错误场景** | 应用运行一段时间后，所有数据库请求都报错：`Connection is not available, request timed out after 30051ms`。日志中连续出现 `No operations allowed after connection closed` |
| **错误原因** | MySQL 服务端 `wait_timeout` 默认 8 小时断开闲置连接，但 HikariCP 的 `maxLifetime` 配置大于 MySQL 的 `wait_timeout`，导致连接池中的连接被 MySQL 服务端关闭后池内未及时剔除。后续请求拿到"已关闭"的连接后触发验证失败，连接池重试直至耗尽所有连接 |
| **错误类型** | 数据库连接池配置错误 |
| **错误文件** | `bank-backend/src/main/resources/application.yml`（HikariCP 配置） |
| **解决方案** | 调整 HikariCP 的 `max-lifetime` 小于 MySQL 的 `wait_timeout`（建议 600000ms=10分钟），并设置合理的 `validation-timeout` 和 `connection-test-query` |
| **经验教训** | 数据库连接池的 `maxLifetime` 必须小于数据库服务端的连接超时时间。部署时需根据 `SHOW VARIABLES LIKE 'wait_timeout'` 的实际值进行配比 |

## 错误 7：前端异步操作缺少错误提示

| 字段 | 内容 |
|------|------|
| **错误时间** | 2026-05-05 (贯穿整个前端开发周期) |
| **错误场景** | 前端所有 API 调用的 `catch` 块均为空（`catch (e) {}`），网络错误或后端异常时用户看不到任何提示，页面卡在加载状态 |
| **错误原因** | 初期开发为了快速实现功能，省略了错误处理逻辑，未对用户进行友好的异常提示 |
| **错误类型** | 用户体验/错误处理缺失 |
| **涉及文件** | `bank-frontend/src/views/home/Home.vue`（第 154 行、第 173 行）、`bank-frontend/src/views/transfer/Transfer.vue`（第 140 行、第 173 行）、`bank-frontend/src/views/ai/AiChat.vue`（第 226 行、第 233 行、第 253 行）等多个文件 |
| **解决方案** | 所有 `catch` 块应至少展示 toast 提示（`this.$toast.fail('操作失败，请重试')`），并可在开发环境打印错误日志 |
| **经验教训** | 前端开发应遵循"所有 API 调用必须有错误处理"的原则。空 catch 块会掩盖问题，让用户困惑 |

## 错误 8：前端 CSS 变量命名与引用不一致

| 字段 | 内容 |
|------|------|
| **错误时间** | 2026-05-05 (前端样式优化阶段) |
| **错误场景** | 部分页面样式渲染异常，CSS 变量未能正确应用 |
| **错误原因** | 主题变量定义在 `theme.css` 中，但部分 Vue 组件使用了未在 `theme.css` 中定义的 CSS 变量，或在 `scoped` 样式中变量引用路径不正确 |
| **错误类型** | 样式/UI 错误 |
| **错误文件** | `bank-frontend/src/assets/styles/theme.css`、`bank-frontend/src/views/ai/AiChat.vue`、`bank-frontend/src/views/home/Home.vue` |
| **解决方案** | 统一使用 `theme.css` 中定义的变量，避免自定义散落变量；使用 CSS 变量时提供 fallback 值（如 `var(--bg-color, #f5f5f5)`） |
| **经验教训** | 设计系统（Design System）的 CSS 变量应在单一文件中统一定义并作为唯一数据源，组件内不应再自行定义散落变量 |

## 错误 9：前端转账页面金额字段使用 `type="number"` 导致精度丢失

| 字段 | 内容 |
|------|------|
| **错误时间** | 2026-05-05 (前端开发阶段) |
| **错误场景** | 用户在转账页面输入金额如 0.01 时，底层精度计算可能出错 |
| **错误原因** | Transfer.vue 中金额输入框使用 `type="number"`（第 44 行），HTML number 输入框对小数精度支持有限，且会对科学计数法、前导零等做非预期处理 |
| **错误类型** | 前端输入格式错误 |
| **错误文件** | `bank-frontend/src/views/transfer/Transfer.vue` 第 44 行 |
| **解决方案** | 使用 `type="digit"`（Vant 的数字键盘）或 `type="text"` + `inputmode="decimal"` 配合前端格式化 |
| **经验教训** | 金额输入应使用专门处理数字/小数输入的组件，避免使用标准 `type="number"` |

## 错误 10：Docker 中间件部署配置顺序问题

| 字段 | 内容 |
|------|------|
| **错误时间** | 2026-04-23 |
| **错误场景** | Docker Compose 部署时 MySQL 和 Redis 中间件启动后，Spring Boot 应用因数据库未就绪而启动失败 |
| **错误原因** | Docker Compose 中缺少 `depends_on` + `healthcheck` 的健康检查依赖配置，Spring Boot 在 MySQL 完全就绪前就开始初始化连接池 |
| **错误类型** | 部署/DevOps 错误 |
| **错误文件** | `f:\code\bank\bank\docker-compose.yml` |
| **关联提交** | commit `f9a3fbd` - "修正后端docker中间件部署" |
| **解决方案** | 添加 `depends_on` 条件依赖和健康检查（`healthcheck`），确保应用容器在中间件就绪后再启动 |
| **经验教训** | 多容器部署时必须处理服务间的启动顺序依赖，不能假设服务瞬间可用 |

## 总结

### 错误类型统计

| 错误类型 | 数量 | 占比 |
|----------|------|------|
| 数据处理/序列化 | 2 | 20% |
| 并发/竞态条件 | 2 | 20% |
| 业务逻辑错误 | 1 | 10% |
| 安全/加密错误 | 1 | 10% |
| 配置错误 | 2 | 20% |
| 前端错误处理 | 1 | 10% |
| 部署/DevOps | 1 | 10% |

### 关键经验教训

1. **Redis 操作必须注意数据类型的一致性** — BigDecimal 等复杂对象存储需通过 String 中转
2. **分布式锁必须使用原子操作** — SETNX（setIfAbsent），禁用 `hasKey`+`set` 模式
3. **同类功能必须统一考虑安全机制** — 新增支付功能时需复用转账已有的防重、限额等机制
4. **查询条件应优先使用类型/状态字段** — 而非依赖金额正负等间接判断
5. **加密数据操作必须添加异常保护** — 避免单条数据异常影响整个功能
6. **数据库连接池配置必须与服务端保持一致** — maxLifetime 要小于数据库 wait_timeout
7. **前端所有 API 调用必须有错误处理** — 空 catch 块会严重影响用户体验
8. **金额输入应使用专用组件** — 避免 HTML `type="number"` 的精度问题
9. **容器化部署必须处理服务依赖** — 使用 healthcheck 确保服务就绪顺序
